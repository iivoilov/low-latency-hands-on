# Hardened PITCH ingestion and the SipHash C++ baseline

Experiment date: 13 November 2026. A separate EPYC sender transmits to the Ryzen
receiver. The selected C++ baseline uses secret-keyed SipHash-2-4 and accepts
collisions normally. The [implementation security description](../../processors/README.md#input-validation-and-resource-protection)
documents the protections and their limits.

## What changed

Both C++ and Rust now enforce a configurable budget of **1,000,000 simultaneously
live orders** by default, validate message fields before handling absent order
references, distinguish fatal errors from the narrowly skippable errors after
loss, and remove empty symbol/price-level state. Receivers bind to the selected
multicast destination/interface; UDP sender addresses are not checked or trusted.
Queues and sample storage remain bounded. These application-level protections
are required in both languages.

Only C++ required the additional hash defense. It retains `std::unordered_map`
for order IDs and `std::map` for price levels, using SipHash-2-4 over eight
little-endian ID bytes. A fresh 128-bit key comes from OS entropy before RX;
entropy failure aborts startup. Unit Clear retains the key and allocation.
Neither keys nor per-ID hash values are reported. Rust retains standard
`HashMap` with `RandomState`, which already supplies chosen-ID hash-flooding
resistance; its price-level containers remain `BTreeMap`.

The earlier hardened C++ control used an OS-seeded XOR salt and a fatal
16-entry bucket cutoff. The cutoff could reject valid orders because collisions
do not establish malicious intent. The new baseline removes it. JSON identifies
`order_hash: "SipHash-2-4"` and `max_order_bucket_entries: null`.

The hash threat model permits chosen input IDs without secret-key access or a
useful hash/bucket/timing oracle. SipHash supplies practical collision-attack
resistance, not a deterministic worst-case lookup bound. There is no tree
overflow structure. These protections do not authenticate the feed or guarantee
availability: an injector can still forge messages or trigger the existing
fatal-input policy with malformed input.

The C++ specialization follows the [official SipHash reference](https://github.com/veorq/SipHash),
with [CC0 attribution](../licenses/SipHash-CC0.txt). Sixteen eight-byte known-answer
cases cover varied keys and the published length-eight vector. A separate
10,000-case differential check against the independent C reference passed.
Reference file hashes accompany the result data.

## Validation

All functional checks ran on the native Ryzen receiver before timing:

| Check | Result |
| --- | --- |
| GCC 14.2 Release full CTest, including multicast | 6/6 |
| Clang 19.1 Release full CTest | 6/6 |
| GCC Debug ASan + UBSan full CTest, normal handlers | 6/6 |
| Python benchmark unit tests | 24/24 |
| Rust native debug / release | 11/11 each |
| Shared Rust CLI / multicast suites | Both passed |
| Previous hardened C++ GCC Release CTest | 6/6 |
| Previous snapshot Rust release / CLI / multicast | 11/11 and both suites passed |

The new C++ regression constructs 32 IDs in one actual bucket with both a fixed
test key and a normally randomized book. It checks acceptance beyond the former
cutoff, modification, execution, deletion, duplicate detection, Unit Clear and
continued processing after loss. Both native suites fill a million-live-order
book, reject a further Add, and verify capacity reuse. Shared tests cover
malformed fields after loss, destination isolation with different sender IPs,
state budgets and book validity. Functional multicast fixtures run on receiver
loopback; timing trials use the separate EPYC sender.

No packages, host tuning or NIC settings were changed. Public packaging does
not rerun or alter the historical measurements: the result data identifies
measured binaries and source fingerprints. Internal repository history and
operational inventories are not distributed.

## Timing method

The receiver is a native Debian 13 Ryzen 9 9950X, using a 1 Gbps r8169 NIC.
The sender is a separate native Debian dual-EPYC 7742 system using its 1 Gbps
active-backup bond. See the [hardware inventory](../../configs/hardware.json).

C++ uses GCC 14.2.0, C++20, Release `-O3 -DNDEBUG`, without LTO or
`-march=native`. Rust uses rustc 1.99.1 / LLVM 23.1.1, release opt-level 3,
LTO false, 16 codegen units and the default target CPU. The sender uses GCC
12.2.0, `-O3 -DNDEBUG`; old/new sender hashes are identical.

RX CPU 2 and L2 CPU 3 are separate physical cores sharing receiver L3. Startup
allocation runs on CPU 3; the external observer uses CPU 15. Thread masks are
verified before READY and observed during processing. The sender inherits OS
placement. These CPUs are not exclusive reservations. Builds and functional
suites finish before timing starts.

All profiles use version-2 synthetic PITCH, seed 43, unit 1, AAPL/MSFT/SPY,
ten levels per side and three initial orders per level. Each replay has 180
initialization updates, 1,000,000 measured updates, up to eight updates per
packet and 125,024 transmitted datagrams. There are approximately 180 live
orders; this is not a dense million-live-order timing experiment.

| Profile | Background / peak payload Mbps | Burst / period ms | Scheduled seconds |
| --- | ---: | ---: | ---: |
| P1 | 8 / 20 | 10 / 100 | 22.309 |
| P2 | 4 / 20 | 5 / 100 | 42.775 |
| P3 | 8 / 20 | 25 / 250 | 22.292 |
| P4 | 12 / 20 | 20 / 100 | 15.098 |

Three repetitions compare previous hardened C++, SipHash C++ and the unchanged
Rust reference across all four profiles: **36 planned trials**. Both C++
versions reserve and limit state at one million live orders, isolating this
comparison from the earlier reservation increase. Rust is unchanged for this
final hash comparison, though it received the shared application hardening
relative to the original public implementation.

A `random.Random(20261113)` stream shuffles profiles within rounds, revision
order and runner input implementation order. The runner applies its repeat-one
shuffle. Exact execution order is retained. All attempts are preserved without
automatic retries. Playback preloads the file and uses `--spin`, with no
per-packet file output. Late deadlines shift without catch-up bursts.

`CLOCK_MONOTONIC` measures from successful `recvmsg` return to each sampled L2
update, including ring wait, earlier packet messages, allocations, clock reads
and scheduling. Warmup and protocol controls are excluded. NIC/kernel delivery
before RX returns is excluded; this is not wire-to-L2 or cross-host one-way
timing. Percentiles use nearest rank. Summaries are medians of per-run values,
not pooled percentiles. Validity requires complete samples, matching final L2,
successful exits, continuity and verified placement. Sender packet counts and
achieved rates are checked separately.

## Results

All **36/36** trials were valid, each with one million samples, matching final
book and verified affinity. Every sender transmitted 125,024 datagrams. No
kernel/ring drops, missing messages, sequence errors, protocol errors or
truncations were reported. All achieved payload rates were within 5% of the
scheduled finite-file rate. No attempt was retried or excluded.

Three-run medians, **microseconds**, previous XOR/cutoff → SipHash:

| Profile | C++ p50 | C++ p99 | C++ p99.9 |
| --- | ---: | ---: | ---: |
| P1 | 0.320 → 0.400 | 0.560 → 0.810 | 0.640 → 1.070 |
| P2 | 0.330 → 0.410 | 0.570 → 0.810 | 0.750 → 1.090 |
| P3 | 0.320 → 0.400 | 0.560 → 0.740 | 0.680 → 1.040 |
| P4 | 0.320 → 0.400 | 0.560 → 0.780 | 0.670 → 1.070 |

The unchanged Rust reference, also in microseconds:

| Profile | p50 | p99 | p99.9 |
| --- | ---: | ---: | ---: |
| P1 | 0.360 | 0.860 | 1.200 |
| P2 | 0.370 | 0.850 | 1.110 |
| P3 | 0.360 | 0.850 | 1.060 |
| P4 | 0.360 | 0.870 | 1.130 |

C++ p50 increased by **80 ns (24.2–25.0%)**. This measures replacing XOR plus
chain scanning/rejection with SipHash-2-4 and normal collision handling. It does
not isolate hash arithmetic from bucket placement, cache and allocation effects.
Hash keys vary by run and are not recorded. C++ and Rust retain different
hashing policies and container layouts; these numbers do not establish a
language-wide performance ratio.

Only three repetitions are available and CPUs are not exclusively isolated.
The maximum individual RX-to-L2 interval was 265.050 µs; maximum sender schedule
slip was 50.020 ms. All per-run percentiles, maxima, achieved rates, losses,
queue wait and execution order are retained in the
[JSON data](2026-11-13-siphash-results.json); [CSV summaries](2026-11-13-siphash-results.csv)
provide per-profile medians. Raw inventories, connection details and operational
logs are not distributed. The selected baseline prioritizes collision acceptance
and practical hash-flooding resistance while retaining the measured cost.
