# RX-to-L1 on the selected Ryzen receiver

Measurement date: 2026-11-14, Asia/Nicosia. Scope and affinity audit corrected
on 2026-11-15. The selected comparison is the EPYC host streaming to the Ryzen
receiver. All **60/60 trials** in that direction were loss-free, collected one
million samples and matched the independent L2/L1 oracle.

The original report incorrectly presented an additional 60 reverse-direction
runs as a second receiver benchmark. Those runs were an unrequested scope
expansion. The EPYC host is a busy shared streamer; no empirical NUMA/L3/thread
placement study qualified it as a receiver. A topology inventory and reuse of
Ryzen CPU numbers do not provide that qualification. Those records are preserved
as **unqualified diagnostics**, with no receiver-performance ranking here.

## Hosts and measurement boundary

Both hosts report native Debian kernel `6.12.117+deb13-amd64` in this run.
The Ryzen 9 9950X host uses the 1 Gbps r8169 interface. The dual-socket
EPYC 7742 host uses the 1 Gbps X550 active-backup bond; its active member is
`eno1` in this experiment. The earlier reverse-direction report observed another
kernel and active member. No network, bond, NIC, IRQ, governor, clock or queue
settings were changed for this experiment.

Every selected receiver trial pins RX to CPU 2, the book/L1 thread to CPU 3 and the observer to
CPU 15. Startup runs on CPU 3 before final thread placement, preserving first
touch on the receiver CPU domain. On the selected Ryzen receiver, these book/RX CPUs are separate physical
cores sharing one 32 MiB L3 in its single NUMA node. This placement comes from
the earlier receiver affinity experiment. The EPYC streamer retains OS-selected
placement; its busy-server workload can affect send timing and arrival patterns.
Achieved rates and schedule slip remain part of the records.

### Audit of the 60 receiver affinity records

Pinning is performed by `benchmark/pin_processor.py`, not inside either
processor binary. The launcher sets each TID's mask and checks it before
forwarding READY to the sender. An independent re-read of all 60 saved
`affinity.json` files on 2026-11-15 found:

| Receiver role | Runs checked | Requested CPU | Initial/last-observed effective mask | Sampled CPUs | Migration delta |
| --- | ---: | ---: | --- | --- | ---: |
| RX | 60 | 2 | `[2]` / `[2]` | `[2]` | 0 in every run |
| Book / L1 | 60 | 3 | `[3]` / `[3]` | `[3]` | 0 in every run |

All 60 records also specify observer CPU 15, startup CPU 3 and no monitor error.
Each worker has at least 61 periodic observations. `inherited_allowed_cpus`
describes the launcher's original eligibility before assignment; the effective
worker masks are under `roles.rx` and `roles.l2`. Those masks demonstrate that
the receiver threads were assigned. The processor's own JSON does not contain
this external launcher's affinity record.

The [complete audit](2026-11-15-rx-l1-affinity-audit.json) contains every TID,
initial/last-observed mask, sampled CPU set, observation count and migration delta,
plus hashes and paths of the saved metadata. Effective observations are also
included in each baseline run in the results JSON. Affinity does not isolate
CPUs, eliminate preemption/background work or strictly bind memory. Periodic
observations are not a complete scheduler trace; the migration deltas cover
the interval between the initial and last observations.

`CLOCK_MONOTONIC` measures from immediately after successful `recvmsg` return
to each sampled message's internal L1 emit/no-update decision. It includes RX
bookkeeping, ring wait, preceding messages in the datagram, framing, decoding,
L2, trade history, allocations and the decision. Initial market warmup and
protocol controls are excluded from samples. Callback dispatch/reporting is
after the decision; the default sink performs no external I/O.
Percentiles use nearest rank. This is not NIC/physical-wire latency or CPU time.
Cross-host clock synchronization is not required for this local interval.

Earlier experiment tables measured RX-to-L2. Their absolute values cannot be
used to isolate the packed decoder's effect: this run also includes L1/trades
and expanded protocol semantics. There is no paired byte-versus-packed
end-to-end control in this matrix. See the
[decoder-only experiment](2026-11-14-zero-copy-decoder.md) for that comparison.

## Workloads and independent L1 oracle

All four PCAPs use version 2, seed 43, three symbols, unit 1, 180 warmup adds,
1,000,000 measured market updates and 125,024 datagrams. At most eight updates
share a packet. Default live-order and retained-trade limits remain one million.
The order book is sparse; this is not a million-live-order capacity test.

| Profile | Background / peak payload Mbps | Burst / period ms | Scheduled seconds |
| --- | ---: | ---: | ---: |
| P1 | 8 / 20 | 10 / 100 | 22.309 |
| P2 | 4 / 20 | 5 / 100 | 42.775 |
| P3 | 8 / 20 | 25 / 250 | 22.293 |
| P4 | 12 / 20 | 20 / 100 | 15.098 |

Timing traffic contains Add Long, Execute, Reduce Long, Modify Long and Delete,
plus Time and Unit Clear controls. Executions update last trade. Other equities
layouts are covered by functional fixtures, rather than represented in these
timing profiles. Playback preloads the PCAP, uses `--spin`, writes no per-packet
send log and shifts late deadlines instead of catching up with a burst.
Payload rates, sender lateness and cumulative schedule slip are recorded.

An independent Python wire decoder reconstructed orders, quantities, executions,
best quotes and each emit/no-update outcome before timing. Its final L2 matched
the existing manifests. Each profile yields the same final L1 state and:
**1,000,180 decisions, 347,603 L1 emissions, 652,577 suppressions and 246,427
retained executions**. Decision/emission counts include warmup; the latency
sample count excludes it. Every valid run was checked against those counts and
the full final bid/ask/last/metadata state.

A valid run also requires successful sender/receiver exits, continuity, current
book, one million samples, exact final L2, correct timing boundary, verified
affinity and all 125,024 sender calls completed. Achieved-rate conformance is
reported separately and is not silently treated as a loss counter.

The executed schedule shuffled profile, direction and input build ordering
using seed 20261114. The existing runner applied its documented repeat-one build
shuffle. The 60 selected-direction trials were interleaved with 60 unrequested
reverse diagnostics; all 120 ran sequentially and remain in the archive. Each
scheduled trial was attempted once. An
invalid receiver stops on its first loss; the sender completes its workload and
the batch continues to the next independent trial.

## Selected-direction validity and limits

All 60 selected-direction trials were valid and loss-free. Every run had one
million measured samples, correct final L2 and L1, the expected emit/suppress
counts, verified receiver affinity and all 125,024 sender calls completed.
All 60 achieved sender averages were within 5% of the scheduled finite-file
rate. Sender queue drop increases were zero around these profile groups.

There are three repetitions per condition, without confidence intervals or CPU
isolation. Receiver background activity, preemption and the busy streamer's
arrival timing remain possible influences. No NUMA, L3 or thread-affinity
qualification of the EPYC host as a receiver is claimed. Earlier L2-only
measurements have a different endpoint and cannot isolate the packed decoder's
end-to-end effect.

## Archived reverse diagnostics

The extra 60 reverse-direction attempts produced 14 feed-valid and 46 invalid
records: all 45 higher-rate trials failed, plus one low-rate GCC O3 trial.
Feed validity establishes continuity and oracle agreement, not a qualified
receiver placement or a meaningful CPU comparison on a busy shared server.
Their latency values remain in the JSON and separate diagnostic CSV solely
to preserve the experiment history; they are excluded from the main summaries.

The low-rate round-two GCC O3 failure stopped after 36,936 measured updates
with an eight-message gap. The sender qdisc counter did not increase for that
group; aggregate receiver drop counters do not identify which traffic was
lost. No specific cause is assigned. The high-rate diagnostic groups recorded
sender queue drop increases. These facts are not receiver-performance results.

The receiver's missing-message count is its first bounded sequence gap, not
the total file loss after it exits. Partial samples, RX/socket/ring statistics,
sender queue counters and actual rates retain their separate meanings in the
archive. No timing attempt was retried or erased.
