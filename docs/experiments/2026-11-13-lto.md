# LTO on the current processor baseline

Experiment date: 2026-11-13, Asia/Nicosia. EPYC sends; ryzen receives.
This compares GCC whole-program LTO, Clang ThinLTO/full LTO and Rust thin/fat LTO against fresh controls, using the selected SipHash C++ implementation and unchanged Rust source.

## Summary

All **96/96** planned trials passed. Every trial collected 1,000,000 measured updates, matched the final book and verified RX/L2 affinity. All senders transmitted 125,024 packets, and all achieved rates were within 5% of the scheduled finite-file rate. No attempt was retried or excluded.

## Build modes and provenance

The source is the preserved baseline revision `96fa5d5a8275998e1b0d5878d584f5689614f94c`. Executable sources were checked against the current checkout and the preserved source manifest; sender/receiver source identities and workload hashes were checked by the existing runner. Builds use separate fresh directories in the preserved snapshot, with no source deployment or source edits.

C++ uses C++20, `-O3 -DNDEBUG`, the default target CPU and the existing warning flags. Rust uses opt-level 3, **16 codegen units in every mode**, the default target CPU and the locked dependencies from the existing offline cache. No `-march=native`, target-CPU tuning or PGO is used.

| Compiler | Mode | Added build setting |
| --- | --- | --- |
| GCC 14.2 | Control | No LTO flag |
| GCC 14.2 | Whole-program LTO | `-flto=4` at compile and link |
| Clang 19.1 | Control | No LTO flag |
| Clang 19.1 | ThinLTO | `-flto=thin` at compile and link |
| Clang 19.1 | Full LTO | `-flto=full` at compile and link |
| rustc 1.99.1 / LLVM 23.1.1 | Current control | `CARGO_PROFILE_RELEASE_LTO=false` |
| rustc 1.99.1 / LLVM 23.1.1 | Thin | `CARGO_PROFILE_RELEASE_LTO=thin` |
| rustc 1.99.1 / LLVM 23.1.1 | Fat | `CARGO_PROFILE_RELEASE_LTO=fat` |

GCC has no LLVM ThinLTO mode. Its `-flto=4` enables whole-program LTO with up to four parallel LTO code-generation jobs. GCC’s `-ffat-lto-objects` means storing native code alongside LTO intermediate code; it is not the equivalent of LLVM full/fat LTO. See the [GCC optimization documentation](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html).

Clang uses the installed LLVM 19 archive tools and LLVMgold plugin with GNU BFD ld 2.44. The same linker is used for its no-LTO control. No linker/package installation was needed. Clang’s [driver documentation](https://clang.llvm.org/docs/CommandGuide/clang.html) defines thin versus monolithic full LTO.

Rust’s current `lto = false` **retains local ThinLTO within each crate across codegen units**. The comparison enables cross-crate thin or fat LTO relative to that current setting; it does not measure `lto = "off"`. The [Cargo profile documentation](https://doc.rust-lang.org/cargo/reference/profiles.html#lto) describes these distinctions. Environment overrides select each mode without changing Cargo.toml; verbose rustc commands confirm thin/fat and 16 codegen units.

## Workloads and measurement

The receiver is native Debian 13 on a Ryzen 9 9950X with a 1 Gbps r8169 NIC. The separate EPYC 7742 sender uses the existing GCC 12.2 `-O3 -DNDEBUG` executable through a 1 Gbps bond. Exact kernel, CPU policy, NIC/driver, compiler, binary hash and source metadata accompany the JSON.

RX CPU 2 / L2 CPU 3 / observer CPU 15 match the selected baseline. Startup allocations run on CPU 3. The sender inherits OS placement. These masks do not exclude unrelated OS work. All builds and functional suites finish before timing; no host/NIC tuning or package installation is performed.

All four PCAPs are version 2, seed 43, AAPL/MSFT/SPY, ten levels per side, three initialization orders per level, unit 1, 180 warmup updates and 1,000,000 measured updates. There are at most eight updates per packet. The live book has approximately 180 orders; the default reservation and limit remain 1,000,000 simultaneously live orders.

| Profile | Background / peak payload Mbps | Burst / period ms | Scheduled seconds |
| --- | ---: | ---: | ---: |
| P1 | 8 / 20 | 10 / 100 | 22.309 |
| P2 | 4 / 20 | 5 / 100 | 42.775 |
| P3 | 8 / 20 | 25 / 250 | 22.293 |
| P4 | 12 / 20 | 20 / 100 | 15.098 |

Three rounds each run all four profiles and all eight builds: 96 trials. A `random.Random(20261113)` stream shuffles profile and runner input build order; the unchanged runner applies its documented repeat-one shuffle. The exact execution order is retained. Independent trials continue after invalid results without retrying them.

Playback preloads each PCAP, uses `--spin`, writes no per-packet send log and shifts late deadlines to avoid catch-up bursts. The receiver uses benchmark stop-on-loss. Validity requires successful exits, continuity, current book, exactly one million samples, the final-book oracle and verified affinity; sender packet counts are independently checked.

`CLOCK_MONOTONIC` measures from immediately after successful `recvmsg` return to the internal L2 update endpoint. Ring wait, earlier messages in the datagram, allocations, instrumentation and scheduling are included. Warmup and controls are excluded. LTO can change the entire executable, including timing-call overhead; this does not isolate hashing or book arithmetic. Percentiles use nearest rank. Summaries are medians of individual valid-run percentiles, not pooled samples.

## Interpretation and limits

GCC full LTO reduces median p50 by 10 ns on every profile (2.5–2.6%). Median p99.9 improves by 0.9–4.6%. The executable shrinks by 31.1%. This is a small, consistent improvement on this workload; the individual tail ranges still overlap in several conditions. GCC full LTO is the useful optimization candidate from this comparison.

Clang thin and full LTO both increase median p50 from 350 to 360 ns (2.9%) on all four profiles. ThinLTO p99.9 increases by 1.0–3.1%; full LTO ranges from a 1.0% improvement to a 3.1% regression. Their smaller binaries provide no general latency advantage here. Clang without LTO is faster than GCC without LTO in this matrix, but that is a separate compiler comparison.

Rust thin LTO leaves median p50 unchanged on three profiles and improves P2 by 10 ns (2.8%). Median p99.9 changes range from a 10.8% improvement on P4 to a 6.9% regression on P2. Rust fat LTO adds 60–70 ns to p50 (16.7–20.6%) and worsens median p99.9 by 5.0–9.6%, despite reducing executable size by 18.6%. Keep the current Rust setting for a consistent reference; fat LTO is a latency regression in this experiment. Thin LTO is a profile-dependent tradeoff.

Symbol and disassembly inspection confirms that the executable changes extend into the processing path. GCC full LTO has no standalone `Processor::process` or `OrderBook::apply` entries, whereas its control has both. Rust’s emitted `Processor::process` body grows from 1,738 bytes in the current build to 3,767 with thin and 4,677 with fat LTO; the separate `apply_inner` entry disappears under both LTO modes. This is evidence of changed inlining and function layout. It does not identify the cause of the latency differences: no hardware-counter profiling or controlled inlining experiment was performed.

The reference build settings remain those of the selected baseline; this investigation records candidate optimizations without silently replacing historical controls.

The effect should be judged within each compiler and profile. Clang-versus-GCC differences also include different optimizers; Rust-versus-C++ differences include container layout, standard-library hashing and implementation choices. Hash keys vary between runs by design and are not logged.

There are only three repetitions per condition, with no confidence intervals or exclusive CPU isolation. Small differences near one clock-read step need caution. The workloads are legitimate sparse synthetic books, not dense million-live-order or adversarial-input timing tests. There is no saturation-throughput, NIC-to-L2 or synchronized cross-host latency measurement.

Across all trials, the largest individual sampled RX-to-L2 interval was 265.491 µs. The largest sender schedule slip was 46.145 ms. Queue-wait aggregates include warmup packets and are retained separately; they must not be subtracted from sampled-message percentiles.
