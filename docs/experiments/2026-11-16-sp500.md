# Broad S&P 500 universe: RX-to-L1 compiler comparison

Experiment date: 2026-11-16, Asia/Nicosia. Status: 18/18 timed trials complete and valid.

The new prepared set spreads one million updates across 503 S&P 500 stocks,
using dated reference prices and 30,180 initial orders. Generation is the only
stage that reads price/universe inputs. Replay preserves the prepared bytes and
schedule, and both processors retain their existing measurement contract.

## Why two traffic profiles

The [previous selected-direction matrix](2026-11-14-rx-l1.md) contains 60 valid
runs over four profiles and five builds. For the three O3/release variants:

| Previous profile | GCC O3 p50 / p99.9 µs | Clang O3 p50 / p99.9 µs | Rust p50 / p99.9 µs |
| --- | ---: | ---: | ---: |
| P1: 8/20 Mbps, 10/100 ms | 0.730 / 2.460 | 0.660 / 2.280 | 0.800 / 2.660 |
| P2: 4/20 Mbps, 5/100 ms | 0.740 / 2.480 | 0.670 / 2.310 | 0.810 / 2.450 |
| P3: 8/20 Mbps, 25/250 ms | 0.720 / 2.450 | 0.660 / 2.280 | 0.800 / 2.790 |
| P4: 12/20 Mbps, 20/100 ms | 0.720 / 2.470 | 0.660 / 2.270 | 0.800 / 2.810 |

C++ ordering and central latency barely changed across those profiles. Rust's
p99.9 varied by about 15% from lowest to highest, including a different ordering
relative to GCC in P2. Thus two profiles are a reasonable routine suite for the
requested fixed 8/20 Mbps comparison, with repetitions retained; they do not
replace a rate sweep when investigating load dependence or loss thresholds.
Keep the old four-profile results and recipes available for that purpose.

S1 retains P1's short bursts; S2 retains P3's longer bursts. Both have a 10%
burst duty cycle and 9.2 Mbps cycle average, so burst duration/frequency varies
without changing average offered load. Neither changes background to compensate
for bursts. The packet payload sequence and random event choices are identical
between S1/S2; the PCAP deadlines differ.

## Universe, reference prices and synthetic behavior

The constituent source is the [S&P 500 CSV](https://github.com/datasets/s-and-p-500-companies/blob/main/data/constituents.csv),
cross-checked against the [iShares IVV holdings download](https://www.ishares.com/us/products/239726/ishares-core-s-p-500-etf/latest-holdings.csv).
The archived holdings snapshot is dated November 13, 2026, the preceding trading
day. Every one of the 503 constituent symbols has a USD reference price. The
nonmember HOLX residual holding and SKYD warrant are excluded. BRK B and BF B
are normalized to BRK.B and BF.B. These are vendor reference prices from fund
holdings, not independently verified official exchange closing prints; the
provider notes that vendor prices can have different effective dates.

`simulator/import_sp500.py` reads previously downloaded files with the Python
standard library, requires complete price coverage, and freezes integer prices
and source hashes. The dated CSV, provenance, both PCAP/manifest pairs and raw
downloads remain ignored generated artifacts. A later download is a different
input snapshot, not a reproduction of this one. See the
[preparation recipe](../../simulator/play_files/README.md#broad-stock-universe).

`prepare_feed --universe` accepts `symbol,price_1e4` CSV rows. It initializes ten
levels per side and three orders per level, one-cent steps from each symbol's
reference price. Modifications independently select a level on the same side;
prices remain within ±$0.10. The generator's bounded order-slot limit increases
from 4,096 to 65,536; processors keep their existing one-million-live-order and
one-million-retained-trade limits. Legacy default three-symbol workloads retain
their version 2 prices and random sequence. Explicit-price workloads use version
3 and freeze reference prices in their manifests.

Each active order slot has equal selection probability. With equal geometry,
this distributes activity across all symbols; a deleted/exhausted order is
replenished in the next event. Per-symbol measured update counts range from
1,847 to 2,132 in this seed. This models a broader working set and independently
selected securities, but activity weights, order sizes, correlations, spreads
and volatility are not fitted to observed exchange traffic. There is no claim
of a statistically realistic market or intraday price model. Purchased option
EOD records are not used.

## Human-monitor implications

An independent wire reconstruction counts each symbol only when its L1 state
changes, excluding initialization. Among full fixed-width schedule windows:

| Window | S1 mean active stocks | S2 mean active stocks |
| --- | ---: | ---: |
| 10 ms | 125.25 | 125.53 |
| 100 ms | 475.64 | 472.68 |
| 1 second | 503.00 | 503.00 |

All 503 symbols change during each of the 22 full one-second windows in either
profile. A one-second monitor throttle can therefore still show synchronized
rows: subscription snapshots initialize per-symbol timers together, and an
active symbol has a pending conflated change when its next interval expires.
Increasing the universe alone does not guarantee random-looking UI refreshes.
These are scheduled-wire activity counts, not a browser end-to-end measurement.
No throttle semantics or monitor code changed, and monitoring is disabled in
all timed runs. Lower display intervals can expose more independent activity;
changing timer phases or fitting per-symbol activity is separate follow-up work.

## Workloads and validation

The prepared set is `simulator/play_files/sp500-20261113-seed44/`.
Each profile uses seed 44, unit 1, at most eight updates per packet, 503 symbols,
30,180 initialization adds, 1,000,000 measured market updates and 128,774 packets.
The initialization boundary comes from the manifest; a raw receiver default of
180 would be incorrect for these files. Controls are excluded from samples.

An independent Python decoder reconstructs all orders, levels, executions and
L1 emit/no-update outcomes directly from wire bytes. Both files match their
final L2 manifests and produce 1,030,180 L1 decisions, 350,353 emissions,
679,827 suppressions and 246,211 retained trades, including initialization in
the decision/emission counts. Each valid timed trial also matches every final
bid/ask/last/metadata field for all 503 symbols. Raw oracle output and complete
final states remain archived; the portable JSON records hashes and counts.

## Execution and measurement

The separate EPYC 7742 streamer sends to the Ryzen 9 9950X receiver. Receiver
RX CPU 2 and book/L1 CPU 3 are separate physical cores in one 32 MiB L3 domain;
startup allocations run on CPU 3, and the external observer runs on CPU 15.
No reverse-direction trials were requested or run in this experiment.
The existing 1 Gbps r8169 receive path, MTU 1500 and OS policies are retained.
No packages, NIC/IRQ settings, governors, BIOS settings or system services change.
Only the benchmark processes receive explicit affinity masks.

Both hosts run Linux 6.12.117+deb13-amd64. GCC 14.2.0 and Clang 19.1.7 use
`-O3 -DNDEBUG`, default target CPU, without LTO. The sender is built with GCC
14.2.0. Rust is 1.99.1 with LLVM 23.1.1. Rust uses its
release profile: opt-level 3, LTO false and 16 codegen units. C++ keeps keyed
SipHash and standard unordered/map containers; Rust keeps RandomState HashMap
and BTreeMap. These are comparisons of these implementations and toolchains,
not an isolated language effect. Sources/builds are fresh isolated copies of
the current working tree, preserving older deployments and uncommitted work.

The six profile/round groups and build ordering are reproducibly shuffled,
with three repetitions for each of two profiles and three builds: 18 trials.
The runner additionally applies its documented build-order shuffle. Streaming
uses preloaded `play_feed --spin`, no per-packet disk output, and shifts late
deadlines instead of catching up. Achieved rates and schedule slip are recorded.

`CLOCK_MONOTONIC` starts immediately after successful `recvmsg` return and ends
after each sampled message's L1 emit/no-update decision. It includes ring wait,
earlier messages in a datagram, parsing, state updates and allocations. This
is userspace RX-to-L1 elapsed latency, excluding NIC/kernel work before return;
it is not physical-wire latency or cross-host one-way latency. Percentiles use
nearest rank. Tables report medians of per-run percentiles, not pooled samples.

## Results

All **18/18 corrected-batch trials** were valid and loss-free. Each contains one million measured samples and exact final L1/L2 oracle agreement. All sender averages were within 5% of the scheduled finite-file average.

| Profile | Build | Valid / 3 | p50 µs | p99 µs | p99.9 µs | Run p99.9 range µs | Median sender Mbps |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S1 | GCC O3 | 3/3 | 1.490 | 3.220 | 3.920 | 3.880–5.250 | 9.19493 |
| S1 | Clang O3 | 3/3 | 1.350 | 2.910 | 3.570 | 3.560–3.580 | 9.19493 |
| S1 | Rust release | 3/3 | 1.510 | 3.230 | 4.520 | 4.430–4.520 | 9.19500 |
| S2 | GCC O3 | 3/3 | 1.480 | 3.200 | 3.880 | 3.880–3.890 | 9.19183 |
| S2 | Clang O3 | 3/3 | 1.360 | 2.930 | 3.590 | 3.560–3.590 | 9.19079 |
| S2 | Rust release | 3/3 | 1.510 | 3.250 | 4.510 | 4.320–4.520 | 9.19149 |

Clang has the lowest median p50, p99 and p99.9 in both profiles. Compared with GCC, its median p50 is about 8–9% lower and p99.9 about 7–9% lower. Rust p50 is close to GCC, with a higher p99.9. These observations are specific to the implementations, selected builds, workload and placement.

The two profiles reproduce the same build ordering and have similar median percentiles: per-build p50 differs by at most 10 ns and p99.9 by at most 40 ns. Two profiles with three repetitions are sufficient for this routine fixed-rate comparison. One S1 GCC run reached 5.250 µs at p99.9 versus 3.880–3.920 µs in its other repetitions; it remains in the table and no cause is assigned. Keeping repetitions matters more than adding nearly redundant profiles here.

S1 is scheduled for 23.215546 seconds and S2 for 23.223046 seconds, including initialization. All 128,774 send calls complete in each trial. Achieved payload averages range from 9.19060 to 9.19750 Mbps; cumulative sender schedule slip ranges from 17.312 to 27.273 ms. These rates describe delivered offered load, not maximum processor throughput. Kernel/ring drops, missing-message counts and sequence errors are zero in all 18 reports. Sender qdisc drop deltas are zero in each group; unrelated interface traffic remains a separate diagnostic.

All 18 saved affinity records show initial and last masks `[2]` for RX and `[3]` for book/L1, sampled CPU sets 2/3 and zero recorded migration deltas. Every source file matches its deployed hash after the experiment, and processor binary hashes match those captured for every trial. Affinity sampling does not establish exclusive cores or provide a complete scheduler trace.

## Verification and attempts

Local Release build and all 11 offline CTest checks passed, including fabricated
503-symbol regression coverage, exact wire/book/price-band reconstruction,
determinism, schedule checks and invalid universe inputs. All three local
network CTests passed with socket access. Their first sandboxed invocation was
denied socket creation and is retained as an environment limitation. The local
benchmark Python unit suite passed 32 tests.

The first remote preflight exposed a missing standard `<algorithm>` include
for `std::copy_n` in an existing recovery-archive test under GCC 14. The one-line
include fix is retained, as is the failed build log. Corrected remote tests
include 14/14 CTests under each of GCC and Clang, 4/4 sender simulator tests,
18/18 Rust native tests, its documentation-test command (zero doc tests), and
the shared Rust CLI/multicast suite.

The first timing batch mistakenly selected `build/gcc-o3/play_feed` on the
sender instead of the built `build/sender/play_feed`. It was interrupted;
three zero-sample receiver reports, missing-executable/timeout evidence and an
interrupted second group are preserved under
`analysis/sp500-2026-11-16/infrastructure-001/`, with remote raw artifacts in the
postflight archive. It produced no complete latency samples. The corrected
batch uses fresh `-002` result directories. No feed-loss attempt is retried or
removed, and infrastructure attempts are excluded from successful timing tables.

Portable [CSV](2026-11-16-sp500-results.csv) and
[JSON](2026-11-16-sp500-results.json) retain the six summaries and every corrected
batch trial. Raw commands, inventories, affinity records, source snapshots,
workload/oracle files, build/test logs and failed attempts remain under
`analysis/sp500-2026-11-16/`. There are three repetitions without CPU isolation
or confidence intervals; shared-host activity and sender jitter remain limits.
Historical three-stock runs use different workloads and source snapshots, so
an absolute before/after difference does not isolate the effect of symbol count.
